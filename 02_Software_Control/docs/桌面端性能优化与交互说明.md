# 桌面端性能与交互优化（2026-11-27）

## 实测瓶颈与结果

在用户确认机构停稳、断开原控制台后，通过同一 ST-Link 对同一 F407 进行只读 SRAM 测速，没有写入邮箱、复位、暂停 CPU 或启动电机。

| 测量 | 原 CubeProgrammer CLI | 持久 USB / SWD |
| --- | ---: | ---: |
| 读取同样的 200 字节 SRAM | 3 次中位数 420.7 ms | 30 次中位数 3.62 ms |
| 新连接建立 | 每次 CLI 调用重新建立 | 首次约 512 ms，之后复用 |
| 持久读取最大耗时 | — | 5.67 ms |

约 116 倍是**本次内存读取路径**的比较，不是电机按钮全链路或机械动作的加速倍率。原每帧请求至少需要一次 CLI 写入和一次 CLI 读取，加上前置检查、两轴轮询及电压/电流读取，按钮到实际执行容易积累数秒延迟。改动后，持续通信使用同一个 USB 句柄，只有建立会话时解析 ELF 并核对固件。完整动作仍包含 RS485 应答、状态校验、实际运动和到位确认。

原始只读测量结果位于 `desktop/.runtime/performance-readonly.json`。本次没有做实机运动测速。

## 通信与调度

- `stlink_memory.py` 使用固定版本 pyOCD 的 ST-Link 命令层和内存接口；不创建目标 Session，不执行 halt/reset/flash。实际测速前后 CPU 都处于运行状态。参见 [pyOCD ST-Link 支持说明](https://pyocd.io/docs/debug_probes.html#stlink)。
- `PersistentBridgeLink` 保留原固件邮箱，所有读写由一个工作线程串行执行。帧数据、长度和解锁值写入后，最后用一个对齐的 32 位写发布请求；实时写入仅限 F407 SRAM。
- 打开、固件校验、协议错误或关闭失败都会释放 USB；通信故障不自动重发运动，不自动改用另一条链路继续运动。
- 若环境未安装 pyOCD，保留原 CLI 兼容模式；界面标明兼容模式。当前项目虚拟环境已安装 `desktop/requirements.txt` 中的固定版本依赖，macOS 原启动脚本会优先使用该环境。
- 后台反馈改为逐轴轮询，在报文边界优先处理操作队列。停止先分别向两台发送 FE，再查询停稳，避免第一台的诊断读取挡住第二台停止。
- 状态、实际位置和轨迹到位检查保留；电压、电流改为约 2 秒一次的低优先级读取，运动时暂缓电气遥测。界面保留最近一次有效电压、电流，不将其视为实时值。
- 未修改固件代码和邮箱布局；若已经使用上一版双轴故障修复固件，本次只需重启桌面端，不需要为性能改动再次烧录。

## 操作体验

- 单电机 / 扇扫俯仰保留独立入口，使用清晰的分段导航；单电机选择与双轴动作作用范围明确区分。
- 两轴位置、目标、使能独立显示为信息卡片；“下一步”根据连接、使能、中心标定和运行状态给出指引。
- 每次提交指令立即显示处理状态，异步连接细分为通道打开、固件校验、总线连接及两轴初始反馈。
- 连接和未知时长的检查使用活动进度条；定位进度来自实际位置与本次目标，不用估计时间冒充完成百分比。扫描显示当前段数，整体完成后才报告“往复扫描已完成”。
- 进度区域显示耗时，保留本次完成用时；运行期间锁定运动参数，停止按钮 / Esc 始终可用。串口参数在连接后折叠，操作日志保留在底部。
- 模拟测试覆盖了优先调度、两轴停止顺序、邮箱发布顺序、禁止 Flash 写入、连接失败资源释放、即时进度、参数锁定、状态指引和 1060×800 的布局边界。
